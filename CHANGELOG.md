# Changelog

All notable changes to Forgeline. Versions follow [semantic versioning](https://semver.org/): 1.0.0 is the full release, a major addition bumps the minor number, a bug fix bumps the patch number. The changelog starts with Phase 2.

## Unreleased (0.2.0)

### Added
- Cargo workspace, pinned toolchain, GitHub Actions for format, clippy and tests on Linux and Windows, and a repo hygiene test that keeps saves, dumps, packs and extracted data (and any other commit identity than the allowed ones) out of git. Reviewed and tested by VeroxAUS
- A headless RAM check in CI (`forgeline --headless-check`) that fails above 20 MB private bytes and writes a machine-readable results file (`bench/results/`), plus `docs/ram-log.md`. Reviewed and tested by VeroxAUS
- Automatic discovery of the Steam account, library, Wilds install, build ID and save files (read-only, via `libraryfolders.vdf` and the app manifest), the data-directory rules that refuse Steam, the install and the save folder, and `forgeline-check discover` for PC test rounds. Reviewed and tested by VeroxAUS
- A fixture save builder (`tools/fixture-builder`) that writes small invented saves in the real container format, with expected values next to each, and two committed fixtures. Reviewed and tested by VeroxAUS
- The save reader (`forgeline-save`): opens the save container with the Steam ID, walks the class stream without building a tree of it, and summarises each character slot (equipment box, item box, pouch, found flags, monster kills, active slot). `save-diff` lists which fields differ between two save copies, and `forgeline-check save` reports the counts for PC test rounds. Reviewed and tested by VeroxAUS
- The pack reader and exe scan (`forgeline-pak`): indexes the game's original `re_*.pak` files (never `pak_mods`), reads single entries (stored, deflate, zstd, chunked), resolves a hand-written list of the game files we need by path hash, and rebuilds the save's class and field names from the game exe in a moment (route A), plus `forgeline-check pak` to report all of it. Untested against the real install until the PC round. Reviewed and tested by VeroxAUS
- The update flow (`forgeline-update`) and `forgeline --update`: finds the game and the save, extracts only the needed files from the game's packs into a staging folder in the app's own data folder, rebuilds the save's class names from the exe, checks the result against the last good data (missing files, shrunk categories, files that do not open, an older build or a lost class block it) and swaps it in only if it passes, keeping the old data as `previous`. The second update with nothing new says `Unchanged`. `forgeline-check update` runs it into a dev data folder and can simulate a missing file to see the gate reject it. It runs at below-normal priority, writes only under the data folder and reports progress through `update-status.json`. Untested against the real install until the PC round. Reviewed and tested by VeroxAUS
- The engine (`forgeline-engine`): a low-priority worker thread that keeps one `Snapshot` (what was found, the save summary, the data status and a patch notice) up to date. It shows the last view from a small cache at once, checks in the background whether the save changed, and wakes only on the operating system's file notification (no timer, no polling), after the save has been quiet for 0.5 s. A change during a recompute runs once more; a half-written or locked save keeps the old summary and shows an error. The save is only read: opened with sharing, read whole into memory and checked for unchanged size and modified time. `forgeline-check engine` reports how fast the view appears and how long a new save takes to show up, `forgeline-check midwrite` rewrites a copy of a save slowly (and, on Windows, locks it) under the engine to show that a half-written or locked save never gives a wrong view, and the headless RAM check now includes the engine. Untested against the real save until the PC round. Reviewed and tested by VeroxAUS
- The UX sample screen (`tools/ui-sample`, a dev tool outside the app): one Build-like screen in seven style variants drawn in real egui, with CPU-rendered screenshots in `docs/ux/samples/`. The maintainer locked in D3 as the style, and the style guide is written from it next. Reviewed and tested by VeroxAUS
- The UX app shell (element 2, in `tools/ui-sample`): the D3 left rail with a section divider, and a status line with synced, recomputing and problem states, laid out from the window size, with screenshots in `docs/ux/samples/shell/`. A dev tool, not yet part of the app. Reviewed and tested by VeroxAUS
- The UX icon pipeline (element 3, in `tools/ui-sample`): icons load on one background-priority thread, shrink to 64 px and sit in a 1 MB memory cache that drops the least recently drawn icon, with the plain glyph while loading and when there is none. Tested with synthetic icons only; whether the game's icon files are readable is still open. A dev tool, not yet part of the app. Reviewed and tested by VeroxAUS
- The UX build card (element 4, in `tools/ui-sample`): the weapon, five armour pieces and the charm as D3 rows with icon tiles, decoration slot circles (one size, level as a number, hover tooltip) in fixed columns next to the Owned or Missing word, and an empty-slot row. The whole UI now scales with the window (1 to 3 times the 1000 by 700 design size). Sample data only, labelled as such, with screenshots in `docs/ux/samples/build/`. A dev tool, not yet part of the app. Reviewed and tested by VeroxAUS
- The UX skills strip (element 5, in `tools/ui-sample`): the build's skills beside the equipment rows, one round dot per level with the level number at the right. Set and group skills are pinned at the top with a `SET` or `GROUP` tag and one line per tier. Long builds collapse those rows and leave out the least important skills behind a clickable `+N more on Why`, and a 16:9 window gets a second column. Sample data only; tier text is invented because whether the game files hold it is unverified. Skill counts of real endgame builds are researched in `docs/research.md`. A dev tool, not yet part of the app. Reviewed and tested by VeroxAUS
- The UX headline blocks (element 6, in `tools/ui-sample`): damage and toughness in the Build header, each a label, a `MODELLED` tag, a headline word, a bar and one detail line, sitting on the same columns as the equipment rows and the skills strip. The maintainer chose the Compare option (a tick for current gear and the change against it); the Word and Number options stay in the sample. Unknown values say `UNKNOWN` with the reason. Sample numbers only; the bar scale and word thresholds are provisional until the optimizer exists. Screenshots in `docs/ux/samples/headline/`. A dev tool, not yet part of the app. Reviewed and tested by VeroxAUS
- The UX must-have chips (element 7, in `tools/ui-sample`): a row of equal-size chips (116 by 24 points, four across at the base size and at 16:9) above the equipment on the Build screen, each a skill name and the lowest level wanted. `+ Add` lists skills not yet chosen, a click on a chip sets its level or removes it, and `+N more` (from five must-haves) opens a list of the rest. Long names are cut with an ellipsis (about 14 characters) with the full name on hover. A must-have the unlocked gear cannot reach gets an amber chip and a line under the title. A change keeps the last build on screen and shows a non-blocking `UPDATING` note, with a repaint only while it is pending. Sample data only; the Add list is invented and needs search once real skills exist. Screenshots in `docs/ux/samples/chips/`. A dev tool, not yet part of the app. Reviewed and tested by VeroxAUS
- The UX Solo or Multiplayer switch and alternatives row (element 8, in `tools/ui-sample`): a 30 high two-half switch and six equal icon cells (Best, Safe, Defensive, Monster, General hunting, Gogma) in the Build header, with a tooltip, the chosen name after the breadcrumb, and a dimmed cell with a reason when an alternative is not available yet. A change keeps the last build on screen with the non-blocking `UPDATING` note. The "pieces need parts" line moved to the WEAPON label row. Sample data and invented numbers only; icons are placeholder shapes. Screenshots in `docs/ux/samples/alternatives/`. A dev tool, not yet part of the app. Reviewed and tested by VeroxAUS
- The UX monster selector (element 9, in `tools/ui-sample`): the Monster cell of the alternatives row opens a 300 wide search panel with recent picks, monsters, Guardian and Arch-Tempered on a 28 point row grid (eight rows show, the rest scroll) and a `TEMPERED` switch that limits the list to monsters with a Tempered version. A pick names the build in the breadcrumb (plain ellipsis plus tooltip for long names) and recomputes without blocking. Each row reserves five cells for weak elements, empty while unknown, for the food plan's matchup later. The 38-entry roster comes from public pages (`docs/research.md`) and is not yet checked against the game files. Screenshots in `docs/ux/samples/monster/`. A dev tool, not yet part of the app. Reviewed and tested by VeroxAUS
- The UX shopping list (element 10, in `tools/ui-sample`): the Shopping section with three views (by monster, by piece, by upgrade path) on a 36 point row grid, each item with its icon tile, the monster or pieces it is for, `owned/need` and `Missing N`. Only what is still missing is listed and the counts come from the save, so there is nothing to tick off; the monster with the biggest gap comes first. A piece filter chip narrows every view. The by-monster view has a toggle between `Most items` (default) and `Finishes pieces`. `Missing N` on a Build row now shows the missing items (item, count, monster) on hover and opens Shopping by piece, filtered to that piece, on click. A farm place column draws only when drop data is confirmed (open question 12), so it is absent for now. Sample data only: item names are real Wilds materials from a public page, and which monster drops what is illustrative. Screenshots in `docs/ux/samples/shopping/`. A dev tool, not yet part of the app. Reviewed and tested by VeroxAUS

### Fixed
- The update flow writes nothing into a data folder that sits inside Steam, the install or a save folder: refusing one used to create the folder and a status file there, including when finding the game failed first. A damaged manifest on the last good data now blocks an update, with a message saying how to recover, instead of skipping the comparison; a manifest from another version of the app only warns, so a format change cannot lock updates out. The engine puts the previous data back at start when an update was cut short between its two renames. Reviewed and tested by VeroxAUS
