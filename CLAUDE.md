Forgeline (MH Wilds Build Planner) standing rules (from Thomas, revised 2026-10-27):

Runs alongside the game: while Wilds is running the app must be light. Low idle CPU, memory and GPU, and no polling when nothing has changed. Heavy work (extraction, optimizer search) is fine when the user triggers it, but it runs off the UI thread at low priority so the game never stutters.
Snappy above all: the app opens fast and shows the last build from cached data immediately; a recompute after a save change never blocks the UI. A feature that adds a step before seeing the build, or noticeable start-up time or RAM, does not ship. Check cold start and recompute time on Thomas's PC with Wilds running before a feature ships. A performance budget will be drafted with Thomas.
Read-only on the game: never write to, move or delete the Wilds save files, the game install or the Steam folders. Analyse copies, never the live win64_save folder. Take performance numbers from Thomas's PC with Wilds running.
Never inject into, hook or read the memory of the running game. Never copy or unpack whole game packs (the main one is about 41 GB); extract only the files needed.
Never print or commit secrets or personal data: tokens, keys, Thomas's save files, decrypted save dumps (they hold hunter IDs) or extracted Capcom data. Saves, dumps and extracted data stay out of git and out of the Nexus package. Anyone working on the project provides their own local saves.
Tools: every tool is our own, written in Rust. Each new tool, built or third-party, needs Thomas's yes before it is created or run. MHWeditor has no licence (all rights reserved): its code, type dumps and close rewrites never enter the repo. One thread may study it and write facts in its own words to docs/research.md with credit; the code is written by a separate thread from those notes only. Don't put any third-party code in the repo without recording its licence in THIRD-PARTY-NOTICES.md; GPL code stays out until the licence review says what a Nexus release must be. If a Nexus release requires open source, the project goes open source.
System: Windows and Steam only. Rust everywhere. The UI is pure Rust if the Phase 1 comparison (pure-Rust UI vs Tauri vs Electron, measured with Wilds running) allows. The save is Steam\userdata\<steamid>\2246340\remote\win64_save\data001Slot.bin and the Steam ID comes from that folder name; the app auto-picks the active save slot. The game install is found through Steam's libraryfolders.vdf, never hardcoded. Local-only by decision: no listener, no telemetry, no accounts, nothing leaves the machine.
Type data fallbacks, worked in order: A, our own static dumper reading the game's .exe on disk (runs on the user's PC, nothing shipped); B, a hand-written schema for only the classes we need; C, a licence-checked community dump downloaded on update, never shipped (never run injecting tools ourselves); D, mapping fields by hashes and patterns. Last resort if no game data can be read: MHDB data, clearly labelled to the user as older and unsupported.
Product decisions, don't change these without Thomas: it shows the best build makeable now, never a "wait until endgame" build, covering low rank and high rank, and recomputes when the save changes. "Available" gear is anything from monsters the user has unlocked; missing materials go on the shopping list. Presets (solo, multiplayer, safe), a per-monster mode, and alternatives (best, safe, defensive, monster-specific, general hunting, Gogma-specific). Must-haves are hard constraints, damage is calculated, comfort and defence skills are weighted and editable. Comfort skills get a researched baseline for every skill (Phase 4 research round); users can override them. Dark theme only, readable on a second monitor. A bare window built from the debug data viewer exists from Phase 2 and grows each phase; Phase 6 is polish and the equipment display. The extractor and data model cover every weapon from Phase 3. Every weapon is optimized before 1.0.0, refined one at a time with the light bowgun first; each weapon is labelled tuned or generic. The rotation simulator and fight model are out of scope unless Thomas reopens them.
Data: the game files, read from the user's own install, are the source of truth. The MHDB API (dated April 2026) is a cross-check only (and the labelled last resort above). Game facts come from extracted data or a cited source; if something is unverified, say so and never fill it in from memory. Only the update button refreshes data and it never auto-fetches. A new extraction is staged and validated against the last good data before it replaces it: missing items, false upgrades, or builds that score worse after skill, set bonus or weight changes block it. If extraction fails, a format changed or validation fails, keep the last good data and say so visibly; never show wrong data silently. When the game is patched, warn that data may be out of date, and suggest pressing update only when confidence is above 95% that it won't break or worsen builds.
Open questions, don't resolve by guessing and don't change without Thomas: save-ID to data-ID mapping; owned talismans in the save; mapping kills and story flags to unlocked monsters; whether the game files hold skill numbers, Artian and Gogma Artian tables and motion values; how Wilds melding works; licences; what the training dummy displays (Phase 5 or later).
Docs: docs/PLAN.md (overall plan, phases 1 to 8: spikes, foundation, data and progression, light bowgun optimizer, calibration, interface and shopping list, farming/decorations/melding, Artian and Gogma Artian planner; then the other weapons and Nexus packaging). docs/plans/phase-N-name.md: one detailed plan per phase from the agreed template (goal and done, inputs, design with architecture, per-file design, data formats and performance impact, steps with estimates in threads and test rounds, tools, tests, risks, versioning and changelog, review log, time log). Each phase plan is written just before its phase and Thomas reviews and approves it before any work. docs/open-questions.md is written only by the coordinator, recording every question asked to Thomas; answers move to docs/closed-questions.md. Spike and research results go to docs/research.md. CLAUDE.md at the repo root is an exact copy of these instructions. Check the plan before implementing, update it when a phase finishes, and read the code before building a "new" feature.
Versioning: semantic versioning. 1.0.0 is the full release; a major addition bumps x.1.x; a bug fix bumps x.x.1. Changelog from Phase 2.
Honest estimates: the optimizer shows its assumptions (uptime, weak-spot rate, weights) and flags when the best build changes within a plausible range of them. Never present a modelled number as measured. Community reference builds are added by hand with credit, never scraped, and are used as checks and to calibrate comfort weights, not copied as answers.
Code lives in the private GitHub repo VeroxAUS/Forgeline, default branch main. Feature and fix threads work in the cloud on their own branch and open a PR. The default branch is the only long-lived branch; each branch is merged after its test round passes and then deleted. Cleanup and docs-only PRs may go straight to main.
Tests: tests and linters run on GitHub Actions; a PR says they pass. Automated tests never touch Thomas's real save, the real game install or the live MHDB API; they use small fixture saves and fixture data and pass on a machine without Wilds. Cloud threads can't see Thomas's save or install, so a PR touching the reader or extractor says it is untested against the real files.
Test rounds: every PR gets a test round. Only PRs that change what the app reads or shows run on Thomas's PC; the rest are checked in the cloud and reported the same way. Rounds are queued so Thomas has one checklist at a time; each item says what the app should show for Thomas's current save. The coordinator relays results to the threads, merges once tests pass (Thomas has given the go) and reports each merge in detail: what merged, which tests passed. A feature that fails goes back to its thread.
Thomas's PC is only for what only it can do: running the reader and extractor against the real save and install, building, packaging and installing the app. One PC thread per test queue, working in a permanent work folder; it runs whatever commands it needs itself. Ask Thomas before cleaning that folder. Installing the app on Thomas's PC needs Thomas's OK. Don't open Remote Control sessions for anything the cloud can do. After each round the coordinator resolves the PC thread and starts a fresh one next time. Thomas's installed copy and its data cache are reserved; dev and test builds use a separate data directory and are stopped when done.
Communication: Thomas talks only to the coordinator, never to threads; the coordinator relays everything. Threads report to the coordinator, who summarises for Thomas. The coordinator posts short status when a phase finishes, when Thomas is needed, when it starts a thread, and on errors. Suggestions are welcome at any phase.
Usage: keep usage low. Check docs/research.md before researching anything. Thread briefs are short: the plan step and the files that matter. Search big files (dumps, extractions) with tools like jq or rg; never load them whole. At most 2 or 3 threads at once, resolved as soon as their work merges. Batch questions to Thomas. Start a fresh thread per feature instead of reusing an old one.
Model and effort: the default is Sonnet 5.5 on medium. Opus on high only for tricky debugging or a really big feature. xhigh and max only for bugs a high-effort attempt couldn't fix. Thomas switches these, so suggest a switch when the work calls for it. Threads can't reliably read their own effort level.
