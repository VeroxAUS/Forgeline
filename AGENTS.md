Forgeline (MH Wilds Build Planner) standing rules (from the maintainer, revised 2026-10-27):

Runs alongside the game: while Wilds is running the app must be light. Low idle CPU, memory and GPU, and no polling when nothing has changed. Heavy work (extraction, optimizer search) is fine when the user triggers it, but it runs off the UI thread at low priority so the game never stutters.
Snappy above all: the app opens fast and shows the last build from cached data immediately; a recompute after a save change never blocks the UI. A feature that adds a step before seeing the build, or noticeable start-up time or RAM, does not ship. Check cold start and recompute time on the maintainer's PC with Wilds running before a feature ships. A performance budget will be drafted with the maintainer. Looks matter as much as performance: windows follow the agreed UX mock-ups and style guide, and test rounds include a look check next to the performance check.
Read-only on the game: never write to, move or delete the Wilds save files, the game install or the Steam folders. Analyse copies, never the live win64_save folder. Take performance numbers from the maintainer's PC with Wilds running.
Never inject into, hook or write to the running game. The desktop app and the updater never touch the running game. Live data comes only from forgeline-live, a separate, optional program for the overlay that is off by default and switched on by the user after a warning. It only reads the game: screen capture first, then memory with read-only access. It never writes, injects or hooks. It shuts itself off on unknown game versions or bad reads, and talks to the app only through a private one-way channel (an anonymous pipe, never a listener). Never copy or unpack whole game packs (the main one is about 41 GB); extract only the files needed.
App shape: one main app (Forgeline) with two windows: the desktop window (full planner from the save and cached game data) and an optional see-through, click-through, always-on-top overlay window over the game (borderless windowed only) showing the shopping list and save-based info, plus live info when forgeline-live is on. If forgeline-live is off or broken, the overlay falls back to save data and the desktop window never depends on it. forgeline-update is a short-lived child process for data updates. The approved live-data warning text is recorded in docs/closed-questions.md and is shown before live data turns on, with "Keep it off" as the default.
Never print or commit secrets or personal data: tokens, keys, the maintainer's save files, decrypted save dumps (they hold hunter IDs) or extracted Capcom data. Saves, dumps and extracted data stay out of git and out of the Nexus package. Anyone working on the project provides their own local saves. Never put the maintainer's real name or personal email in any repo file, commit or PR; refer to them as "the maintainer" or by the GitHub handle VeroxAUS.
Tools: every tool is our own, written in Rust. Each new tool, built or third-party, needs the maintainer's yes before it is created or run. Exception: Codex and OpenCode are approved as development tooling for the multi-agent experiment (approved 2026-10-29, plan in docs/plans/multi-agent-workflow.md); they are never part of the shipped app. MHWeditor has no licence (all rights reserved): its code, type dumps and close rewrites never enter the repo. One thread may study it and write facts in its own words to docs/research.md with credit; the code is written by a separate thread from those notes only. Don't put any third-party code in the repo without recording its licence in THIRD-PARTY-NOTICES.md; GPL code stays out until the licence review says what a Nexus release must be. If a Nexus release requires open source, the project goes open source.
System: Windows and Steam only. Rust everywhere. The UI is pure Rust if the Phase 1 comparison (pure-Rust UI vs Tauri vs Electron, measured with Wilds running) allows. The save is Steam\userdata\<steamid>\2246340\remote\win64_save\data001Slot.bin and the Steam ID comes from that folder name; the app auto-picks the active save slot. The game install is found through Steam's libraryfolders.vdf, never hardcoded. Local-only by decision: no listener, no telemetry, no accounts, nothing leaves the machine.
Type data fallbacks, worked in order: A, our own static dumper reading the game's .exe on disk (runs on the user's PC, nothing shipped); B, a hand-written schema for only the classes we need; C, a licence-checked community dump downloaded on update, never shipped (never run injecting tools ourselves); D, mapping fields by hashes and patterns. Last resort if no game data can be read: MHDB data, clearly labelled to the user as older and unsupported.
Product decisions, don't change these without the maintainer: it shows the best build makeable now, never a "wait until endgame" build, covering low rank and high rank, and recomputes when the save changes. "Available" gear is anything from monsters the user has unlocked; missing materials go on the shopping list. Presets (solo, multiplayer, safe), a per-monster mode, and alternatives (best, safe, defensive, monster-specific, general hunting, Gogma-specific). Must-haves are hard constraints, damage is calculated, comfort and defence skills are weighted and editable. Comfort skills get a researched baseline for every skill (Phase 4 research round); users can override them. Dark theme only, readable on a second monitor. A bare window built from the debug data viewer exists from Phase 2 and grows each phase; UX design (brief, mock-ups, style guide) starts in Phase 2; Phase 6 is visual polish, the equipment display and the overlay. The extractor and data model cover every weapon from Phase 3. Every weapon is optimized before 1.0.0, refined one at a time with the light bowgun first; each weapon is labelled tuned or generic. The rotation simulator and fight model are out of scope unless the maintainer reopens them.
Data: the game files, read from the user's own install, are the source of truth. The MHDB API (dated April 2026) is a cross-check only (and the labelled last resort above). Game facts come from extracted data or a cited source; if something is unverified, say so and never fill it in from memory. Only the update button refreshes data and it never auto-fetches. A new extraction is staged and validated against the last good data before it replaces it: missing items, false upgrades, or builds that score worse after skill, set bonus or weight changes block it. If extraction fails, a format changed or validation fails, keep the last good data and say so visibly; never show wrong data silently. When the game is patched, warn that data may be out of date, and suggest pressing update only when confidence is above 95% that it won't break or worsen builds.
Open questions, don't resolve by guessing and don't change without the maintainer: save-ID to data-ID mapping; owned talismans in the save; mapping kills and story flags to unlocked monsters; whether the game files hold skill numbers, Artian and Gogma Artian tables, drop and part-break tables, and motion values; how Wilds melding works; licences; what the training dummy displays (Phase 5 or later).
Docs: docs/PLAN.md (overall plan, phases 1 to 8: spikes, foundation, data and progression, light bowgun optimizer, calibration, interface and shopping list, farming/decorations/melding, Artian and Gogma Artian planner; then the other weapons and Nexus packaging). docs/plans/phase-N-name.md: one detailed plan per phase from the agreed template (goal and done, inputs, design with architecture, per-file design, data formats and performance impact, steps with estimates in threads, test rounds and hours, tools, tests, risks, versioning and changelog, review log, time log). Each phase plan is written just before its phase and the maintainer reviews and approves it before any work. docs/open-questions.md is written only by the coordinator, recording every question asked to the maintainer; answers move to docs/closed-questions.md. Spike and research results go to docs/research.md. AGENTS.md at the repo root is the source of these instructions; CLAUDE.md imports it. Check the plan before implementing, update it when a phase finishes, and read the code before building a "new" feature.
Versioning: semantic versioning. 1.0.0 is the full release; a major addition bumps x.1.x; a bug fix bumps x.x.1. Changelog from Phase 2.
Honest estimates: the optimizer shows its assumptions (uptime, weak-spot rate, weights) and flags when the best build changes within a plausible range of them. Never present a modelled number as measured. Community reference builds are added by hand with credit, never scraped, and are used as checks and to calibrate comfort weights, not copied as answers.
Code lives in the public GitHub repo VeroxAUS/Forgeline, default branch main. Everything committed is publicly visible, so check every commit for personal data and Capcom data before pushing. Before starting work, every thread fetches origin and branches from the current origin/main, never from an old local copy (the main history was rewritten once). Before every push, check `git log --format='%an %ae %cn %ce'` for everything being pushed: only the VeroxAUS noreply, Claude's noreply and GitHub's identities may appear. Commit author and committer for the maintainer's work are VeroxAUS <3145728+VeroxAUS@users.noreply.github.com>; never use a personal email address in git. Feature and fix threads work in the cloud on their own branch and open a PR. The default branch is the only long-lived branch; each branch is merged after its test round passes and then deleted. Cleanup and docs-only PRs may go straight to main.
Tests: tests and linters run on GitHub Actions; a PR says they pass. Automated tests never touch the maintainer's real save, the real game install or the live MHDB API; they use small fixture saves and fixture data and pass on a machine without Wilds. Cloud threads can't see the maintainer's save or install, so a PR touching the reader or extractor says it is untested against the real files.
Test rounds: every PR gets a test round. Only PRs that change what the app reads or shows run on the maintainer's PC; the rest are checked in the cloud and reported the same way. Rounds are queued so the maintainer has one checklist at a time; each item says what the app should show for the maintainer's current save. The coordinator relays results to the threads, merges once tests pass (the maintainer has given the go) and reports each merge in detail: what merged, which tests passed. Every merged PR gets a comment that starts "Tested and approved by the maintainer:" and says what the maintainer checked, where (cloud or their PC, with or without Wilds), the result and the pass time in UTC. Each CHANGELOG.md entry from 0.2.0 ends with "Reviewed and tested by VeroxAUS". A feature that fails goes back to its thread. Sessions can't push tags, delete branches or force-push, so releases, tags and branch deletions go on the maintainer's checklist up front (trial arrangement).
The maintainer's PC is only for what only it can do: running the reader and extractor against the real save and install, building, packaging and installing the app. One PC thread per test queue, working in a permanent work folder; it runs whatever commands it needs itself. Ask the maintainer before cleaning that folder. Installing the app on the maintainer's PC needs the maintainer's OK. Don't open Remote Control sessions for anything the cloud can do. After each round the coordinator resolves the PC thread and starts a fresh one next time. The maintainer's installed copy and its data cache are reserved; dev and test builds use a separate data directory and are stopped when done.
Communication: the maintainer talks only to the coordinator, never to threads; the coordinator relays everything. Threads report to the coordinator, who summarises for the maintainer. The coordinator posts short status when a phase finishes, when the maintainer is needed, when it starts a thread, and on errors. Suggestions are welcome at any phase.
Usage: keep usage low. Check docs/research.md before researching anything. Thread briefs are short: the plan step and the files that matter. Search big files (dumps, extractions) with tools like jq or rg; never load them whole. At most 2 or 3 threads at once. Batch questions to the maintainer. One thread per PR, in every phase: each feature, plan step or design element starts in a fresh thread, and the coordinator resolves that thread as soon as its PR merges and its merge duties are done. Never carry a thread on to the next step, PR or phase.
Model and effort: the default is Sonnet 5.5 on medium. Opus on high only for tricky debugging or a really big feature. xhigh and max only for bugs a high-effort attempt couldn't fix. The maintainer switches these, so suggest a switch when the work calls for it. Threads can't reliably read their own effort level.

Coordinator duties: every merge gets a time-log line in the phase plan (exact merge time in UTC and the pass note), the maintainer's answer in docs/closed-questions.md, and a republish of the plan page via tools/plan-page. When a thread cannot push straight to main, these go in a docs PR, which needs its own go from the maintainer. A merge needs the maintainer's explicit go for that specific PR; a style pick is not a merge go, and a go cited from an earlier PR is checked before use. GitHub may delete merged branches itself, so check before putting a deletion on the maintainer's checklist. No donation, sponsor or Ko-fi links anywhere (repo, README, Nexus) unless the maintainer asks. A phase close-out updates the README text, badges, roadmap and banner phase label, and the time log has no placeholders, one elapsed line and no repeated facts. Keep posts and docs tight; the maintainer dislikes repetition.

Multi-agent experiment (started 2026-10-29, plan: docs/plans/multi-agent-workflow.md; delete this section to end it). Threads run in local T3 worktrees branched from a freshly fetched origin/main. Nothing is pushed, tagged or opened as a PR without the maintainer's go for that specific PR. Every change is reported to the maintainer before it is made. Only Claude or the maintainer runs `git commit`; other agents leave changes uncommitted or draft the message. This machine is the maintainer's test PC, so PC test rounds run as a local T3 thread here instead of a Remote Control thread; the PC rules above (one PC thread per queue, work folder, resolved after each round) are unchanged.

Never switch to a paid model or another provider without the maintainer's say.
